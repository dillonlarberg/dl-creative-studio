The irreducible v0

Pressure-tested down every branch of the decision tree. This is the contract: the done-line, what's in, what's deliberately out.

✓ Done when

The cutdown-tracer takes one mp4 (15s → no hard cap) + a picked sampleMusic track and renders a 15.000s · 1080×1920 · 9:16 MP4 — hard cuts on a librosa-detected uniform bar-grid, music baked + tail fade — using real Gemini moment-selection and real Shotstack sandbox, eyeballed in the minimal UI. App wiring is after v0.

In · hard constraints

  • Single mp4, dur ≥ 15s (no hard cap — long-form OK); Gemini via Files API
  • Gemini → structured [{startSec,endSec,score}] (real, behind a Fake)
  • librosa subprocess → detected tempo → uniform bar-grid
  • planCuts: grid owns timing, Gemini owns content; total = 15.000s
  • Hard cuts, 9:16 1080×1920, music baked + fade
  • Render = Shotstack sandbox (watermark OK)
  • ~3 sampleMusic tracks in Firestore, files in GCS, dropdown pick
  • Source + music via long-TTL GCS signed URLs
  • Each unit behind an interface + a Fake (offline vitest)

Out · deferred

  • Multi-creative stitch · outpaint · ordering (M1)
  • App wiring: Cloud Function · OutputDoc · auth · App Check · multi-tenant · React studio
  • Artlist API + vibe→Gemini mapping
  • Real beat-detection cutting · transitions · 30s
  • librosa as Cloud Run microservice (app-wiring)
  • Paid Shotstack key · Veo motion · social posting

Footprint .env: GEMINI_API_KEY · SHOTSTACK_API_KEY · Firebase/GCS creds · local python3+librosa.

00 / MILESTONE 0 · TRACER BULLET

One 70s video → a 15s cut

Before any multi-creative stitching, prove the loop on the simplest case: a single long video, condensed to a beat-synced 15s. No outpaint, no mixed normalization, one source. Everything else builds on this.

A
Your tokens · Gemini

Pick the best moments

Gemini analyzes the 70s video (1fps sample, GCS URI) and returns scored, timestamped segments — the most engaging spans. We select the set that sums to ~15s. Same structured-output pattern as labeling, just temporal.

B
Your code · pure JS

Snap to the beat

Align each selected segment's in/out to the Artlist track's BPM grid; trim so the total lands on exactly 15.000s.

C
Vendor · Shotstack

Assemble + verify

Trims from the one source + the soundtrack track → 15s 9:16 MP4 → OutputDoc. Pass criteria: cuts land on beats, runtime == 15.0s, music baked.

▸ then generalize

Once 70s→15s passes, swap the single-source segment list for the multi-creative pipeline below. Test matrix: 1v+6i → 3v+3i → images-only → 2v-only. The cut-mapping & render stay identical; only the input-prep (outpaint images, pad/crop videos) is added.

01 / PIPELINE · M1 (GENERALIZED)

The flow, end to end

Once Milestone 0 passes, this is the full N-creative flow. Your tokens do the intelligence (label + outpaint + beat math); the vendor does nothing but deterministic pixel concatenation. Color tells you who owns each step.

1
Your tokens · Gemini

Label each creative

Gemini 2.5 Flash tags every clip/image (scene · energy · content-type · has-people · has-text/logo · hook-candidate) as structured JSON. One call per asset, fired in parallel. ~$0.005 & <10s for 6 assets.

2
Your tokens · ad-resize

Normalize to 9:16

Existing ad-resize tool outpaints images to 1080×1920 unless they already qualify. Video clips can't be image-outpainted — they get padded/cropped at the vendor. This step is what de-risks the whole vendor choice.

3
User

Order the clips

Default = upload order (the client's intent). User can drag to reorder. A non-destructive ✨ Suggest order button proposes a re-rank with rationale — preview, accept/reject. Never auto-applied in v0.

4
User + catalog API

Pick the music

User types a vibe → query the licensed catalog by genre/BPM/duration → show 3–5 candidate tracks → user picks one. Catalog-pick beats generation: instant previews, real licensing, BPM comes free.

5
Your code · pure JS

Compute beat cuts

BPM-grid in plain TS: beat = 60/BPM, cut on bars, snap the final cut to exactly 15s or 30s. No Python, no DSP. Maps each clip → a beat-aligned segment.

6
Vendor · Shotstack

Stitch & render

POST ordered clip URLs + per-clip length + a soundtrack track. Async: poll or webhook. ~5–10s render. Zero FFmpeg in our codebase.

7
Platform

Land the output

MP4 → Storage → OutputDoc(kind:'video') under clients/{slug}/apps/video-stitch/. Streams to the UI via the existing snapshot pattern.

02 / ARCHITECTURE

Mostly assembly, not invention

The ad-resize pipeline is the template. video-stitch is a composition of existing agent-callable tools — the north-star thesis in action: tools calling tools.

Reused for free

  • SSRF guard on every remote asset + music URL
  • Source staging + sha256 cache
  • Auth + identity (server-derived createdBy)
  • OutputDoc — kind:'video' already supported
  • 'video-stitch' already in VALID_APP_IDS
  • Manifest registered — just flip preview→live

No longer built in-house

The earlier plan was self-hosted FFmpeg. Outsourcing render to Shotstack deletes that entire surface — no concat filtergraphs, no SAR/fps normalization, no Ken Burns recipes, no Cloud Run.

What's genuinely net-new

  • Orchestration core (the agent-tool seam)
  • Gemini label call + JSON schema
  • BPM-grid + cut-mapping (pure TS)
  • Catalog music client + the wizard UI
◆ The key insight

Running every creative through ad-resize → one canonical 9:16 dimension first collapses the vendor's hardest job (normalizing mismatched inputs) into the trivial case: concatenate identical-spec clips. That's why outsourcing the stitch is now safe — and our generative outpaint is higher quality than any vendor's letterbox/crop.

04 / VENDOR · SHOTSTACK

There's basically no ceiling for us

No documented clip-count or track limit. The only hard cap is a JSON payload size — and that only bites if you inline base64.

∞

Clip / track limit

None documented. The real ceiling is a ~390 KB JSON payload (DynamoDB-backed). With remote URLs, 6–15 clips uses single-digit KB — a ~50× margin. Never inline base64.

6–10
CLIPS · PRACTICAL SWEET SPOT

Reasonable for 15s/30s

≈2–4s per clip. You'd fit 100+ before the payload wall — but 6–10 is the sweet spot for a punchy reel.

~5–10s
RENDER · ASYNC ONLY

Submit → webhook → fetch

POST /render → poll or callback → MP4 URL. Code a webhook, not a blocking wait.

TTL

The one gotcha

Shotstack fetches asset URLs later in a queue — a short-TTL GCS signed URL can expire first. Mint long-TTL signed URLs or pre-ingest.

One timeline.soundtrack with fadeInFadeOut bakes the music across the whole reel. ~$0.20–0.30/min, sandbox output is watermarked (use a paid key for deliverables).

05 / BEAT CUTS

Cut on the bar — in plain JS

"AI decides where to cut to the beat" needs zero DSP for v0 if the catalog gives you BPM. The math is arithmetic.

v0 · BPM grid

Know the BPM → derive everything. Cut on bars (every 4 beats), snap the last cut to exactly 15s/30s. Pure TypeScript.

// 120 BPM · 15s target
beat = 60/120          // 0.5s
bar  = beat * 4        // 2.0s / cut
cuts = 15 / bar         // ~7–8 segments
// last cut snaps to exactly 15.000s

v1 · real timestamps

Swap the grid for Epidemic's Beats endpoint → true downbeat-accurate cuts that handle intros & tempo drift. librosa (Python sidecar) only as a fallback for tracks with no reliable BPM (e.g. a manually-ingested UPM subset). Kept off the main path.

◆ verdict

No Python service needed for v0. JS suffices the moment the catalog returns a BPM.

Cut-mapping algorithm

// beats[] · total = 15 · clips[] · hero{fixedLength}
buildCutPoints(beats, total):
  for k in [8,4,2,1]:            // phrase → bar → ½ → beat
    grid = everyKthBeatWithin(beats, k, total)
    if all segments in [0.6,2.5]s: return snapEnd(grid, total)

place hero on a boundary, snap its END to nearest beat
assign remaining clips → remaining segments:
  fewer clips than segments  → cycle / hold / slow-mo
  more clips than segments   → subdivide longest on finer beat
assert first.start == 0 && last.end == total   // EXACT 15|30s
06 / THE "MASTER AI"

Label now. Auto-order later.

Two halves with very different risk profiles. Split them.

IN v0

Labeling

Gemini 2.5 Flash labels each clip/image via structured JSON (reference assets by GCS URI → skip File API polling). One call per asset, parallel. ~$0.005 & <10s for 6 assets. Pays off independently: powers the video-vs-image guard, captions, filtering, QA.

v1 · ALL AI ORDERING

Ordering

For ad creatives the client usually already has an intended order. So v0 ordering = manual drag only (default = upload order). Every AI-driven path — auto-reorder and the non-destructive ✨ Suggest button — is v1, gated on real demand. Avoids shipping a non-deterministic order to a client on run one.

08 / BUILD · UNITS & TRACERS

Six seams, each proven in isolation

Every unit gets one interface (vendor hidden behind it) and one tracer (a standalone rig to eyeball it) — reusing the two conventions already in this repo: the _shared/ai/ provider-interface pattern from the architecture findings, and the tools/resize-tracer/ harness. The Cloud Function then just composes seams that are already green.

⚠ Outpaint seam — extract, don't reinvent

A clean outpaint interface doesn't exist yet. runOutpaintBatchCore is coupled to ad-resizing's Firestore and returns counts, not an image; the reusable inner edit is duplicated across the function & the tracer (// MAINTAINED IN PARALLEL). The findings doc already prescribes the fix (P2 ImageEditModel + P5.2 / TODO(resize-pipeline-extract)) — video-stitch is just the forcing function. Rules carried from the convention

  • Every vendor interface ships a Fake impl → each tracer's vitest runs no-network, no-env
  • A tiny env-keyed factory picks the impl — swap Artlist→Epidemic, Shotstack→Creatomate, gpt-image-2→Imagen in one line
  • Retry/backoff lives inside each impl, so every provider inherits it
  • Tracer shape = resize-tracer: tsx watch src/server.ts · public/ viewer · fixtures/ + out/ + critiques.jsonl

How much is actually v0?

Yes, v0: the thin interface + one real impl + a Fake for tests, and a tracer per unit. That is the v0 build method — tracers are the system's unit tests.

Defer: the heavyweight DI/factory, multi-provider A/B, full repository layer (P2 / P4 backlog). Add abstraction only when a second impl demands it — no speculative generality.

Build order — tracers green, then compose

  • 4 · stitch-tracer → VideoRenderer (Shotstack): segments + soundtrack → MP4.
