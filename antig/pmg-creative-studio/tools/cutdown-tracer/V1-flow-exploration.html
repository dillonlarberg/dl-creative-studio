Cutdown · V1 · direction-finding

One video in.
One sharp cut out.

A standalone cutdown tool — drop a long video, set a target length, let it propose the sections worth keeping, eyeball them, ship the cut. Later it slots into the bigger video-stitch as one module.

⚠︎ This is an exploration, not a spec. The spine below is a proposal; the forks are the real decisions. Click options to mark your gut preference — then we'll run grill-me to lock the direction before any plan or code.

01 / THE PROPOSED SPINE

The flow, end to end

Five beats. The one in coral is the new thing V0 never had: a place where a human looks before pixels get rendered.

1

Source input

Drop / pick a long video. We probe its true duration (ffmpeg) so nothing downstream runs past EOF.

↓
2

Intent target lengthbrief?

Set the target length (e.g. 15 / 30 / 60s or free). Optionally type a creative brief — “focus on the product reveal”, “the founder’s key points”. This steers selection.

↓
3

Suggest Gemini

The model watches the whole video and proposes cutdown sections — each with a short “why”, a role in the story, and a score. Two-pass: map the beats, then select a coherent subset that serves the brief.

↓
4

Preview & refine the gate

Human looks. Preview the assembled cut, accept / reject / re-roll sections, tweak the brief and re-suggest. Nothing renders for real until you say go. (Fidelity of this preview is a fork below.)

↓
5

Output render

Approved plan → ffmpeg clips → Shotstack → the final cut. Download / share. (Sandbox watermark for now.)

🎵 Where does music go? Music isn’t on the spine yet — and that’s deliberate. Tempo currently drives the cut grid, so music can’t just be a sticker on top. See Fork A. It might even be out of the isolated cutdown tool entirely and live in video-stitch.
01·5 / THE CORE ABSTRACTION

It's all a shell over one call

Every surface — CLI, the local web page, later video-stitch — is just UX wrapped around a single brief-optional function. That's what makes the cutdown tool isolatable. The brain doesn't know or care who called it.

humanInput = ∅ AUTODETECT

Fallback path. The system prompt does the thinking — “find the moments that matter” — and the cuts land in the beat-grid regions we already map. Zero-input mode: drop a video, get a sensible cut. This is V0's behavior, made addressable.

humanInput = "…" STEER

The brief biases which moments win and how they cohere — but it rides on the same grid + same return shape. Same function, richer result. No second code path for the renderer to learn.

Open question this raises for grill-me: does aiCutdown return a plan to preview (sections + timings, human approves, then a separate render()) or does it render straight through? The preview gate (Step 4) argues for plan-then-render — keep the brain and the renderer as two seams.

02 / THE FORKS

The decisions that actually shape it

These are the things I can't pick for you. Click to register a lean; we'll pressure-test each in grill-me.

Fork A · highest stakes

Where does music live — or does it live here at all?

In V0, the track's BPM builds the beat-grid that sets every cut boundary (cuts land on bars so it feels synced). So music is upstream of timing, not a top layer. That makes “add music last” technically awkward — and raises whether music even belongs in a tool whose job is just “pick the moments.”

Music-first v0 today

Pick the track before suggest; its BPM drives the grid; preview is beat-accurate.

▸ matches current engine
No music in cutdown

Cutdown tool outputs a silent, retimed cut. Music is a video-stitch concern. Cleanest isolation.

Music after approve

Approve sections silently, then lay a track and re-snap the grid. Preview changes after music — friction.

Auto-suggest track

Infer a vibe from the video, pick from the catalog, let the user swap. Most “magic”, most to build.

Fork B

Target length & aspect — how much freedom?

V0 was hard-locked to 15.000s · 9:16. “Target length” implies that's now a knob. Every degree of freedom multiplies preview/QA surface.

Presets 15/30/60

A few blessed lengths, 9:16 fixed. Predictable grid math, fast to ship.

▸ recommend for V1
Free slider

Any length in a range (e.g. 6–90s). More flexible, more edge cases in the grid.

Length + aspect

Also expose 9:16 / 1:1 / 16:9. Doubles the render-format matrix.

Fork C

The creative brief — when and how binding?

The brief is the user's voice in selection. Question is whether it's an upfront steer, a refinement after seeing suggestions, or both.

Optional, upfront

Empty = “just make it engaging”. Filled = steer pass 2. Re-editable to re-suggest.

▸ simplest useful
Refine-after

Suggest blind first, then the brief nudges a re-roll. Brief becomes a correction tool.

Required

Force intent up front. Better cuts, higher friction, worse for “just give me something”.

Fork D · defines the feel

How real is the preview at the gate?

This single choice sets the whole UX tempo. A real render is truthful but costs a Shotstack render + ~30–60s wait + watermark on every iteration. A cheap preview is instant but approximate.

Storyboard cheapest

Thumbnails + labels on a timeline. No playback. Instant, zero render cost. Least convincing.

Local rough-cut

Concatenate the source clips in-browser/ffmpeg (no beat-grid, no music). Fast, free, ~truthful on content.

▸ best effort/value
Real render

Shotstack every iteration — exactly the final, but slow + costs credits + watermark each loop.

Fork E

What are we actually building in V1?

The flow above could be a script, a throwaway local UI, or a real studio screen. This decides how much of V1 is plumbing vs. product.

CLI + artifacts tracer++

Extend run-live: emit a suggestions JSON + storyboard, approve via a flag/file, then render. No UI.

Minimal local web UI

One page: upload → suggestions → preview → render. Local only. Proves the UX honestly.

▸ matches “explore UX”
Studio screen

A real app surface (auth, OutputDoc, multi-tenant). Biggest lift; arguably post-V1.

04 / SCOPE LADDER

How much control at the gate?

Refinement power is a ladder, not a yes/no. V1 should pick a rung and stop.

rung 0
Accept all

Take the AI's set as-is. One button. (Basically V0 + a look.)

rung 1 · proposed V1
Accept / reject / re-roll per section + edit brief

Keep or kill each suggestion, ask for another, steer with the brief. No manual frame-trimming.

rung 2
Manual trim & reorder

Drag clip edges, reorder the story. Real mini-editor. Much more UI.

rung 3
Add your own clips / overlays / captions

Full creative surface. This is video-stitch territory, not cutdown.

04·5 / THREE VERSIONS, PICK ONE

Generate 3 cuts. Pick the one you like.

No editing individual cuts. The brain returns 3 distinct full versions, each a complete coherent cut shown as a thumbnail storyboard. You compare and pick one whole version to render — or re-roll for 3 fresh ones. Human taste replaces per-section fiddling.

Render Version B ▸ ⟳ Re-roll all 3 brief: “focus on the demo” ✎ (edit → 3 new versions)

What this means for the brain: one call returns N plans — aiCutdown(video, track, { humanInput?, targetSec, variants: 3 }) → CutdownPlan[]. Each CutdownPlan carries an AI-written description (its pitch — the blue blurb above) plus a per-cut why, so you pick by reading, not just by squinting at thumbnails. No keep/exclude state, no per-slot regeneration. The open functional question is how the 3 versions are made meaningfully different (story angle? emphasis? sampling?) — graded in the next question.

05 / DECISIONS LOCKED

What grill-me settled

  • Music: music-first. User browses the catalog & picks a track → BPM detected → that track is the source of truth for the cuts. The brain receives the track; it never browses.
  • Abstraction: aiCutdown(video, track, {humanInput?, targetSec, variants}) → CutdownPlan[]. Plan-then-render: the brain returns plans, render is a separate seam.
  • Refinement: generate 3 whole versions, pick one. No per-cut editing. Re-roll = 3 fresh versions.
  • Diversity: analyze once, then select 3× by fixed angle — Narrative / Highlights / Punchy. Each angle sets its own playback order. A brief, when present, biases all three.
  • Per-version polish: one lightweight AI self-critique per version (coherence + brief-fit) before it's shown.
  • Each plan carries an AI-written description + per-cut why (pick by reading, not squinting).
  • Preview: storyboard thumbnails (ffmpeg frame-grabs) + description. Final watch = the rendered output (Shotstack).
  • Output: presets 15 / 30 / 60s, 9:16 locked.
  • Surface: functionality first, UI is a thin throwaway shell. Whole flow is V1, built in checkpoints (mirrors M0 gates).
