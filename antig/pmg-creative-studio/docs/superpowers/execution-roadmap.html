Execution Roadmap

2026-05-15 · pmg-creative-studio · branch dev

Three plans on the table. Solo dev. Limited bandwidth. This page is the decision record: what to ship first, in what order, with what depends on what.

Decision

Ship the unified output schema migration first (Plan B, ~3–5 days), then execute the video-cutdown lift (Plan A, multi-week 3-PR convoy). The security plan stays a stub — promoted to a real plan only after Plan B merges, since Plan B supplies the clientSlug denormalization that the security rules will gate on.

Why this order: Plan A's Q3/Q18 lock batches/{batchId} + outputs/{outputId} as its target schema. Doing A first means re-migrating video-cutdown later or shipping a 4th schema variant. Cheaper to migrate two apps now than three apps in a month.

Risk register

High

Plan B deploy gate skipped on a Friday

Task 9 (reader cutover) must not ship before Task 8 (backfill) completes. Make this a literal commit/PR boundary, not a checklist item. Otherwise: stale reads, missing outputs, refresh-to-clear.

High

Wrong assumption that Plan B = secure sharing

Plan B adds clientSlug + createdBy but does NOT enforce per-client isolation. All 8 PMG users still read all clients. Don't tell any stakeholder "data is now isolated per-client" until Plan C ships.

Medium

Plan A PR-B scope creep

Lifting a 4,323-line monolith UI is where weeks turn into months. Pre-commit to a hard cutoff: 6 step components + 3 hooks + 1 widget + 2 E2E tests. Anything else is post-launch.

Medium

uploads/ collection rename ambiguity

Plan B doesn't address that uploadService.ts writes to uploads/ (a path that shouldn't exist post-migration). Either explicitly out-of-scope it in Plan B or fold it in — don't leave it floating.

Low

Server/client type duplication (Plan A)

tsc rootDir prevents importing types across the boundary. Plan acknowledges this; mitigated by shape-parity assertion in tests. Acceptable maintenance cost.
